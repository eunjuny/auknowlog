## 1. 제출형 풀이 UX

### 선택 이유

정답률과 오답 복습은 사용자가 답을 모르는 상태에서 선택했다는 전제가 있어야 의미가 있다. 기존 화면은 선택 직후 정답 색상과 해설을 보여주어, 이후 문항의 풀이 행동과 저장된 정답률을 신뢰하기 어려웠다.

### 적용 내용

- 제출 전에는 선택 상태만 표시하고 정답·해설·근거를 숨긴다.
- 모든 문항에 답해야 `답안 제출`을 활성화한다.
- 제출하면 선택을 잠그고 정답·오답 색상, 해설, 근거, 전체 점수를 표시한다.
- 제출 시 PostgreSQL 풀이 기록과 오답 복습 일정을 자동 저장한다. 저장 API는 같은 퀴즈의 재요청에 기존 기록을 반환해 자동 재시도에서도 중복 기록을 막는다.
- Git 내보내기는 제출·자동 저장 이후에만 허용한다.
- 새 퀴즈를 생성하면 선택·제출·저장 상태를 초기화한다.

### 검증 기준

- 프론트엔드 프로덕션 빌드 성공
- 제출 전 정답·해설 DOM 비노출
- 일부 문항만 선택했을 때 제출 비활성
- 전체 선택 후 제출하면 점수와 문항별 해설 표시
- 제출 후 선택 변경 불가
- 제출 직후 풀이 기록 자동 저장, 저장 중 다음 문제·Git 내보내기 비활성
- 같은 퀴즈에 대한 저장 API 재호출 시 기존 풀이 기록 반환, 복습 일정 중복 생성 방지

### 검증 결과 (2026-08-31)

- `vite build` 성공
- 백엔드 전체 Gradle 테스트 성공
- 2문항 데모 시나리오에서 첫 문항만 선택했을 때 해설 0개, 제출 비활성 확인
- 전체 선택 후 제출 버튼 활성 확인
- 제출 후 해설 2개와 `2/2` 점수 표시, 선택지 잠금 확인
- 제출 후 풀이 기록과 오답 복습 일정이 자동 저장되고, Git 저장은 자동 저장 완료 후에만 활성화됨을 확인

## 2. pgvector 통합 테스트

### 선택 이유

H2의 PostgreSQL 호환 모드는 일반 테이블과 유니크 제약을 빠르게 확인할 수 있지만 PostgreSQL 확장인 `vector` 타입, `<=>` 연산자와 HNSW 인덱스를 구현하지 않는다. 따라서 V3를 H2에서 제외한 기존 테스트만으로는 실제 배포 DB에서 마이그레이션과 검색 SQL이 동작한다고 증명할 수 없었다.

### 적용 내용

- `test`와 Docker가 필요한 `integrationTest` 소스 셋을 분리했다.
- Testcontainers 2.0.5가 운영 Compose와 같은 `pgvector/pgvector:0.8.6-pg16-bookworm` 이미지를 임의 포트에 실행한다.
- Flyway V1~V3를 빈 DB에 적용한 뒤 확장 버전, `vector(512)` 컬럼, HNSW 코사인 인덱스를 DB 카탈로그에서 확인한다.
- 실제 `QuestionVectorRepository` SQL로 유사 벡터는 0.90 임계값에서 차단되고 다른 벡터는 통과하는지 확인한다.
- 임베딩 검사에서 예외가 발생해도 SHA-256 정확 중복 검사와 문제 저장이 계속되는지 서비스 단위 테스트로 확인한다.
- GitHub Actions에서 백엔드 변경 시 `./gradlew check`를 실행해 단위 테스트와 실제 DB 통합 테스트를 함께 검증한다.

### 검증 결과 (2026-09-03)

- 단위·H2 테스트 12개 통과
- 실제 PostgreSQL 16 + pgvector 통합 테스트 2개 통과
- 전체 17개 테스트, 실패·오류·건너뜀 0개
- 로컬 `./gradlew check --rerun-tasks --no-daemon` 성공(17초)
- 라이브 OpenAI API 호출 0회, 토큰 비용 0원
- GitHub Actions 워크플로 구성 완료. 실제 원격 CI 성공 확인은 커밋·push 후 남은 완료 조건

세부 구조, 실행 방법과 테스트의 한계는 [pgvector·Testcontainers 통합 테스트](PGVECTOR_INTEGRATION_TEST.md)에 정리한다.

## 6. 학습 이력·통합 대시보드·간격 반복

### 선택 이유

학습 서비스에서는 사용자가 "얼마나 풀었는가"와 "무엇을 복습해야 하는가"를 바로 이해할 수 있어야 한다. 생성형 AI를 사용하는 서비스라면 학습 지표와 함께 API 호출 성공률, 토큰 사용량, 응답 시간도 확인 가능해야 장애·비용·품질 문제를 구분할 수 있다.

### 적용 내용

- `GET /api/dashboard`가 PostgreSQL의 풀이 기록, 복습 일정, 문제 이력, AI 생성 원장을 집계한다.
- 대시보드는 학습 현황과 AI 운영 현황을 한 화면의 독립 구역으로 나눈다.
- 학습 구역에는 누적 풀이·정답률·문항 수·오늘 복습 수와 최근 14일 학습 추이를 표시한다.
- 운영 구역에는 최근 14일의 호출 수·성공률·토큰·평균/P95 지연시간·모델별 사용량을 표시한다.
- 차트 코드는 대시보드 진입 시에만 지연 로딩하여 문제 풀이 첫 화면의 초기 번들에 포함하지 않는다.
- 프로젝트 DB에 실제 단가를 저장하지 않으므로, 잘못된 비용 추정 대신 토큰·지연시간 원시 지표만 표기한다.
- 풀이 이력의 주제별 정답률, 누적 문항 수, 마지막 학습일을 규칙으로 계산해 우선 보완·이해 강화·복습 주제를 최대 3개 추천한다. 추천 선정 자체에는 LLM을 호출하지 않는다.
- 추천 카드의 `문제 준비`는 주제와 권장 문제 수만 문제 생성 화면에 채우며, 사용자가 데모 또는 AI 생성을 명시적으로 선택하기 전에는 API 비용이 발생하지 않는다.
- 사용자가 직접 고르거나 추천에서 가져온 주제로 1~12주 로드맵과 주간 목표 문항 수를 생성한다. 진행 중인 계획은 여러 개를 동시에 유지하고, 전체 목표 달성 시 `COMPLETED`로 전환해 완료 목록으로 분리한다.
- 로드맵에서 시작한 퀴즈에는 `learning_quiz.roadmap_id`를 연결한다. 주차별 진행률에는 그 로드맵에 연결된 자동 저장 풀이 기록만 반영해, 과거 같은 주제 풀이가 새 목표를 부풀리지 않게 한다.
- 로드맵 화면은 주차별 기간·목표·실제 풀이 수·상태를 보여주고, 현재 또는 미달성 주차에서만 문제 생성 화면으로 이동시킨다.

### 검증 결과 (2026-09-08)

- 학습 워크플로 통합 테스트에서 풀이 1건과 AI 성공·실패 원장을 생성하고 대시보드 집계값을 검증했다.
- 실제 PostgreSQL 16 + pgvector 개발 DB의 `/api/dashboard`에서 누적 풀이 6회, 학습 문항 35개, AI 원장 9건과 최근 14일 시계열 응답을 확인했다.
- 프론트엔드 프로덕션 빌드 성공. 대시보드 차트 번들은 문제 생성 화면의 초기 번들과 분리됐다.
- 학습 워크플로 통합 테스트에서 정답률 50%인 Java 주제가 `WEAKNESS` 추천과 권장 4문항으로 반환되는지 검증했다.
- 같은 통합 테스트에서 2주·주당 2문항 Java 로드맵을 만들고, 로드맵에 연결된 데모 퀴즈 2문항 제출 뒤 진행률이 50%로 집계되는지 검증했다. 로드맵 생성 전 Java 풀이 기록은 진행률에서 제외됐다.
- 실제 PostgreSQL 개발 DB에 Flyway V5~V11(주차·계층형 로드맵, 퀴즈 연결, 자료 출처 메타데이터)을 적용했다. Testcontainers 통합 테스트도 실제 PostgreSQL에서 V1~V11 적용과 대주제·소주제·자료 출처 컬럼을 검증한다.

### 남은 범위

- 오늘 복습 화면에서 대상 문제를 다시 풀고 다음 간격을 계산하는 흐름
- 반복 오답과 세부 개념 태그까지 반영하는 약점 분석
- 여러 주제를 섞는 목표 기반 로드맵과 매주 달성률에 따른 계획 자동 재조정
- Langfuse Trace/OTLP 연동 완료. Prompt Management와 평가셋·실험은 실제 Trace가 쌓인 뒤 도입

## 7. 문제 품질 피드백

### 선택 이유

생성형 AI 문제는 정답률이 높더라도 정답이 복수로 해석되거나 해설이 부족할 수 있다. 학습자의 직접 피드백을 문제별로 수집하면 AI 생성 원장·모델·프롬프트 변경을 품질 신호와 연결할 수 있다.

### 적용 내용

- 답안 제출 뒤 각 문항에서 정답/내용 오류, 모호함, 해설 부족, 유사 문제 반복, 난이도 과소·과대, 기타 의견을 선택할 수 있다.
- `question_feedback`은 문항 ID, 유형, 최대 500자 의견, 상태, 생성·수정 시각을 저장한다.
- 현재 단일 사용자 구조에서는 문항당 최신 피드백 한 건만 유지하며, 같은 문항에서 다시 저장하면 새 행을 만들지 않고 갱신한다.
- 대시보드의 문제 품질 구역에서 전체 수집 수, 확인이 필요한 의견 수, 유형별 건수를 표시한다.
- `비슷한 문제가 자주 나와요(TOO_SIMILAR)`는 같은 주제의 다음 AI 생성에 실제 반영한다. 최신 피드백 문항 최대 10개를 최근 이력보다 우선해 프롬프트 회피 목록에 넣고, 전체 목록은 30개·문항당 50자로 제한한다.
- 생성 후보의 기존 임베딩을 재사용해 피드백 문항에만 코사인 유사도 `0.82` 기준을 적용한다. 일반 중복 기준 `0.90`은 유지하며 추가 OpenAI 임베딩 호출은 발생하지 않는다.
- 향후 인증을 도입하면 유니크 기준을 문항 단위에서 `문항 + 사용자` 단위로 변경하고, 운영자 처리 상태와 재생성 이력을 연결한다.

### 검증 결과 (2026-09-09)

- H2 학습 흐름 통합 테스트에서 피드백 생성 후 같은 문항 의견 갱신, 중복 행 미생성, 대시보드 유형 집계를 검증했다.
- Testcontainers PostgreSQL + pgvector 통합 테스트에서 Flyway V4 적용, `question_feedback` 테이블, 문항별 유니크 제약을 검증했다.
- 프론트엔드 프로덕션 빌드로 제출 후 문항별 피드백 UI를 검증했다.
- 서비스 단위 테스트에서 피드백 문항이 프롬프트의 우선 회피 목록에 포함되고 `0.82` 유사 후보가 제외되는지 검증했다.
- 실제 PostgreSQL + pgvector 통합 테스트에서 일반 기준 `0.90`은 통과하지만 피드백 기준 `0.82`에는 차단되는 벡터를 검증했다.

## 8. Terraform 기반 클라우드 배포

### 선택 이유

로컬 Docker Compose는 개발 환경을 재현하는 데 적합하지만, 실제 운영 환경의 네트워크 경계, 시크릿 주입, 컨테이너 배포와 데이터베이스 운영을 반복 가능하게 만들지는 못한다. Terraform으로 인프라를 코드화하면 콘솔 클릭 과정 대신 Git의 변경 이력과 검토 가능한 `plan`으로 운영 환경을 관리할 수 있다.

단일 백엔드·프론트엔드 서비스의 현 단계에서는 Kubernetes를 먼저 운영하지 않는다. 운영 부담이 더 낮은 ECS Fargate로 컨테이너 배포·네트워크·데이터베이스의 기본을 검증한 뒤, worker 분리나 수평 확장 요구가 분명해질 때 Kubernetes·GitOps를 별도 확장 과제로 검토한다.

### 계획 범위

- `infra/terraform`에 VPC, private/public subnet, 보안 그룹, ECR, ECS Fargate, ALB, RDS PostgreSQL, Secrets Manager 정의를 저장한다.
- GitHub Actions가 테스트·이미지 빌드·ECR 푸시까지 수행하고, 승인된 배포만 ECS 서비스 갱신을 수행하게 한다.
- OpenAI·Langfuse 키와 DB 비밀번호는 Git과 Terraform 변수 파일에 저장하지 않고 Secrets Manager에서 런타임에 주입한다.
- Terraform state는 로컬 파일이나 Git이 아닌 암호화된 원격 backend(S3)와 상태 잠금(DynamoDB)으로 관리한다.
- 배포 전 `terraform fmt`, `validate`, `plan`을 CI에서 실행한다.

### 비용 안전 조건

현재는 이 항목을 구현·실행하지 않는다. `terraform apply`는 실제 AWS 리소스를 만들며 RDS, NAT Gateway, ALB, 데이터 전송 등에서 비용이 발생할 수 있다.

- 적용 전 AWS Pricing Calculator로 월 예상 비용을 문서화한다.
- 별도 개발 AWS 계정과 월 예산 알림(Budgets)을 먼저 만든다.
- 가장 작은 개발 사양과 필요 시에만 실행하는 원칙을 사용한다.
- 검증이 끝난 임시 리소스는 Terraform으로 명시적으로 제거하고, RDS 백업 보존 정책을 먼저 확인한다.

### 완료 조건

- 빈 개발 계정에서 `terraform plan` 결과와 리소스 구성을 검토한다.
- 비용 상한 알림과 시크릿 비노출을 확인한 뒤 제한된 환경에만 `apply`한다.
- GitHub Actions의 테스트·이미지 빌드·배포 파이프라인이 성공하고, 롤백 절차를 문서화한다.

## 9. 단계형 학습 로드맵

### 선택 이유

주차와 문제 수만 있는 계획은 “기초 개념을 이해한 뒤 네트워크로 진행한다” 같은 선수 학습 관계를 표현하지 못한다. 단계별 목표와 선행 관계를 명시하면 로드맵이 일정표를 넘어 실제 학습 순서를 제어할 수 있다.

Mermaid는 결과를 보여주는 시각화 형식으로 사용하고, 로드맵의 원본은 검증과 버전 관리가 가능한 `*.roadmap.json`으로 정한다.

### 적용 내용

- 화면에서 단계, 단계별 문제 주제, 목표 문항 수와 복수 선행 단계를 직접 작성한다.
- 주제와 예상 기간을 입력하고 명시적으로 버튼을 누르면 OpenAI가 범위·난이도·자료 분량에 맞춰 대주제 수, 소주제 수와 목표 문제 수를 결정한다. 고정 개수를 채우기 위한 내용 부풀리기나 생략을 금지한다. 결과는 DB에 바로 저장하지 않고 편집 미리보기로 반환하며, 사용자가 이름·설명·순서·목표 문제 수를 수정하고 최종 확인한 정의만 v1.1 검증 후 저장한다. 최종 저장은 모델을 다시 호출하지 않는다.
- `*.roadmap.json` v1.0·v1.1 파일을 가져오고 계층형 샘플 파일을 내려받을 수 있다.
- 소주제가 없는 대주제는 단독 단계로 진행하고, 소주제가 있으면 등록 순서대로 완료해야 다음 소주제와 대주제가 열린다.
- 서버는 최대 크기, 필드 제한, 중복 식별자, 없는 단계 참조, 자기 참조와 순환 의존성을 저장 전에 검증한다.
- PostgreSQL의 `learning_roadmap_step`, `learning_roadmap_step_dependency`에 실행용 데이터를 정규화하고 원본 JSON도 재현용으로 보관한다.
- 단계에서 만든 퀴즈는 `learning_quiz.roadmap_step_id`로 연결한다. 자동 저장된 풀이 문항 수가 목표에 도달하면 다음 단계가 자동으로 잠금 해제된다.
- 새 로드맵 생성 시 기존 `ACTIVE` 로드맵을 종료하지 않는다. 목록 API는 여러 진행 중 로드맵과 완료 로드맵을 분리해 반환한다.
- 마지막 목표 문제 제출과 같은 트랜잭션 안에서 로드맵 상태를 `COMPLETED`로 바꾸며, 화면은 두 목록을 접힌 카드로 보여주고 선택한 카드의 상세만 펼친다.
- 과거 단일 활성 정책에서 `ARCHIVED`된 데이터도 목표를 모두 달성했다면 완료 목록으로 한 번 자동 정리한다. 미완료 보관 데이터는 임의로 재개하지 않는다.
- 기존 주차형 로드맵 데이터는 삭제하지 않고 조회 호환성을 유지한다.

### 검증 결과 (2026-09-08)

- H2 학습 흐름 통합 테스트에서 파일 가져오기, 첫 단계 잠금 상태, 2문항 풀이 후 첫 단계 완료와 다음 단계 자동 해제를 검증했다.
- 잘못된 확장자와 순환 참조 파일이 HTTP 400으로 거절되는지 검증했다.
- 서로 다른 로드맵 2개가 동시에 진행 중 목록에 유지되고, 한 로드맵의 마지막 목표 제출 후 해당 항목만 완료 목록으로 이동하는지 검증했다.
- 프론트엔드 프로덕션 빌드를 통과했다.
- AI 생성 조립 테스트는 모델을 모킹해 계약 전달과 저장 경계를 검증했으며, 실제 OpenAI 호출은 수행하지 않았다.
- 파일 형식과 흐름은 [`.roadmap.json` 학습 로드맵 형식](ROADMAP_JSON_FORMAT.md)에 별도로 정리했다.

## 10. 안전한 학습 자료 수집

### 선택 이유

로드맵이 사용자의 실제 학습 자료를 기반으로 하려면 파일과 기사 URL을 받을 수 있어야 한다. 그러나 서버가 사용자가 입력한 URL을 그대로 호출하면 클라우드 메타데이터나 사설망을 읽는 SSRF가 될 수 있고, 파일 파서는 위장 파일·대용량 입력에 노출된다. 따라서 AI 연결보다 먼저 입력 경계를 안전하게 만드는 것을 1단계로 정했다.

### 1단계 적용 내용

- `학습 자료` 화면에서 TXT·Markdown·PDF 파일, 공개 HTTP(S) URL, 직접 입력을 선택한다.
- Apache Tika로 실제 파일 형식을 확인하고 PDF 텍스트를 추출하며, jsoup으로 HTML 실행 요소와 메뉴 영역을 제거한다.
- URL은 사설·루프백·링크 로컬·예약 주소, 사용자정보, 비표준 포트를 거절하고 모든 리다이렉트를 다시 검증한다.
- 파일 10MB, URL 응답 5MB, 본문 50,000자, 연결 3초·요청 8초로 자원 사용을 제한한다.
- 추출 결과를 화면에서 수정·확인한 뒤에만 저장한다. 정규화한 본문의 SHA-256이 같으면 기존 자료를 재사용한다.
- 저장 시 `source_document`에 자료 유형, 최종 URL 또는 파일명, MIME 타입, 본문 해시와 처리 상태를 남기고 `source_chunk`에 1,200자 단위 문맥을 저장한다.
- 저장 자료를 AI 로드맵 생성에서 선택할 수 있다. 명시적인 생성 클릭 시에만 앞에서부터 최대 8개 청크를 OpenAI로 보내며, 외부 문서 안의 지시문은 실행하지 않는 데이터 경계를 프롬프트에 둔다.
- 생성된 `learning_roadmap`은 `source_document_id`로 근거 자료와 연결하고 목록·상세 화면에서 자료 제목과 원문 링크를 확인한다.

### 다음 단계

- 사용자별 자료 소유권과 삭제 정책을 추가한다.
- 단계별 근거 청크 인용과 생성 결과의 근거성 평가를 추가한다.
- DNS rebinding의 남은 위험은 배포 환경 egress 정책과 클라우드 메타데이터 차단으로 방어를 보강한다.
- 세부 설계와 운영 제한은 [파일·URL 학습 자료 수집 보안 설계](SOURCE_INGESTION_SECURITY.md)에 정리한다.
