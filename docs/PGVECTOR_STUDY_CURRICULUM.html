01
Representation

임베딩과 512차원 벡터

텍스트가 비교 가능한 숫자 공간으로 바뀌는 과정과 정확 중복·의미 중복의 역할을 구분합니다.

Learning goal

이번 회차가 끝나면 설명할 수 있어야 하는 것

  • 임베딩이 생성형 답변이 아니라 텍스트의 수치 표현이라는 점
  • 512차원이 숫자 512개라는 의미와 차원 축소의 trade-off
  • 코사인 유사도·내적·유클리드 거리의 차이
  • SHA-256 검사와 의미 검사를 한 계층으로 합치지 않은 이유
  • 기본 활성 정책과 환경 변수 차단 스위치가 각각 필요한 이유

Vector basics

512차원 벡터는 숫자 512개의 좌표다

임베딩 모델은 문장을 사람이 읽는 문자열이 아니라, 의미가 가까운 문장끼리 가까운 위치에 놓이도록 숫자 배열로 변환합니다. 각 차원을 “Java 정도”처럼 단독으로 해석하기보다 512개 값 전체의 방향과 상대적 위치를 봅니다. 

"JVM의 역할은 무엇인가요?"
→ [0.012, -0.037, 0.081, 0.004, ..., -0.022]  // 총 512개

"JVM이 Java에서 하는 일은?"
→ [0.010, -0.034, 0.079, 0.008, ..., -0.019]

차원이 커질 때

  • 의미 정보를 더 보존할 가능성
  • 저장·전송·검색 비용 증가
  • 인덱스 메모리 증가

차원이 작아질 때

  • 벡터 저장 공간 감소
  • 거리 계산량 감소
  • 구분 정보 손실 가능성

이 프로젝트의 512차원은 정답이 아니라 초기 운영값입니다. 실제 중복·비중복 문항 쌍으로 품질을 측정한 뒤 유지하거나 바꿔야 합니다.

Similarity

코사인 유사도는 크기보다 방향을 본다

cosine similarity(A, B) = (A · B) ÷ (‖A‖ × ‖B‖)
방식비교 기준이 프로젝트 관점
코사인 유사도벡터 사이의 방향문장 길이보다 의미 방향 비교에 적합
내적방향과 크기의 결합정규화 여부에 따라 크기의 영향이 생김
유클리드 거리좌표 사이 직선거리벡터 크기 차이까지 거리로 반영

pgvector의 <=>는 코사인 거리이므로 현재 SQL은 1 - distance로 유사도를 계산합니다.

SELECT question_history_id,
       1 - (embedding <=> CAST(? AS vector)) AS similarity
FROM question_embedding
WHERE 1 - (embedding <=> CAST(? AS vector)) >= 0.90
ORDER BY embedding <=> CAST(? AS vector)
LIMIT 1;

Layered protection

정확 해시와 의미 벡터는 경쟁 관계가 아니다

계층잘하는 일놓치는 경우외부 비용
SHA-256공백·구두점 차이 정도의 동일 문장표현을 바꾼 같은 의미없음
임베딩 + pgvector표현이 다른 의미 중복 후보임계값·모델 품질에 따른 오판임베딩 API 입력 토큰
임베딩 장애를 “중복 검사를 전부 못 한다”로 처리하지 않습니다. 외부 API가 실패해도 SHA-256 정확 검사는 계속 적용하고, 퀴즈 생성의 핵심 기능을 유지합니다.

Cost boundary

비용은 pgvector가 아니라 임베딩 API에서 발생한다

512벡터 차원
0.90초기 중복 임계값
약 2KB벡터 1개 원시 크기
기본 ON실제 AI 모드의 임베딩

pgvector는 로컬 PostgreSQL의 CPU·메모리·디스크를 사용할 뿐 호출당 요금이 없습니다. 반면 임베딩 모델은 API로 전달한 입력 토큰에 따라 과금됩니다. 짧은 문제 문장에서는 일반적으로 매우 작지만, 비용·지연·rate limit·외부 장애 가능성이 있으므로 화면은 더미 모드를 기본으로 두고, 운영 중에는 환경 변수로 임베딩을 즉시 끌 수 있도록 설계했습니다.

02
Search

PostgreSQL pgvector와 HNSW

벡터를 관계형 원본 데이터와 함께 저장하고, 근사 최근접 이웃 검색으로 빠르게 후보를 찾는 구조를 이해합니다.

Learning goal

이번 회차가 끝나면 설명할 수 있어야 하는 것

  • 별도 벡터 DB 대신 PostgreSQL + pgvector가 적합한 조건
  • vector(512), <=>, vector_cosine_ops의 역할
  • 완전 탐색과 근사 검색의 정확도·속도 차이
  • HNSW의 다층 그래프 탐색 원리
  • m, ef_construction, ef_search 조정 방향

Why pgvector

원본 문제와 벡터의 정합성을 한 DB에서 관리한다

PostgreSQL + pgvector

  • 문제 이력과 FK로 직접 연결
  • 한 가지 백업·복구 체계
  • 로컬·포트폴리오 운영 부담이 작음
  • 관계형 조건과 벡터 검색을 조합 가능

별도 벡터 DB가 필요해지는 시점

  • 수천만~수억 벡터 규모
  • 벡터 검색의 독립 확장 필요
  • 다중 테넌트 격리·분산 샤딩 요구
  • 전용 필터·하이브리드 검색 기능 필요

Auknowlog는 대규모 검색 제품보다 “문제 이력에 의미 중복 검사를 붙이는 학습 서비스”에 가깝습니다. 이 규모에서 별도 검색 클러스터는 정합성·배포·모니터링 부담이 더 클 수 있습니다.

HNSW mental model

상위 계층은 고속도로, 하위 계층은 골목길

희소한 상위 그래프에서 시작

전체 후보를 보지 않고 먼 구간을 크게 건너뛰며 질의 벡터와 가까운 영역으로 이동합니다.

현재 위치의 이웃과 비교

더 가까운 이웃이 있으면 이동하고, 더 나은 후보가 없을 때 한 계층 아래로 내려갑니다.

조밀한 하위 그래프에서 정밀 탐색

후보 집합을 유지하며 가까운 벡터를 찾고 최종 Top-K를 반환합니다.

HNSW는 근사 검색입니다. 완전 탐색보다 빠른 대신 항상 동일한 결과를 보장하지 않으며, 검색 후보 폭을 넓히면 재현율은 올라가지만 지연도 증가합니다.

Tuning

세 가지 핵심 파라미터

파라미터적용 시점높이면대가
m인덱스 생성노드당 연결 수 증가, 탐색 경로 풍부메모리·인덱스 크기·삽입 비용 증가
ef_construction인덱스 생성더 좋은 그래프 품질과 재현율 가능생성·삽입 시간 증가
ef_search검색더 많은 후보를 탐색해 재현율 증가쿼리 지연·CPU 증가

현재 프로젝트는 pgvector 기본값을 사용합니다. 데이터가 적은 상황에서 튜닝값을 먼저 바꾸는 것은 근거가 약합니다. 실제 문항 수와 p95 지연, 중복 판정 재현율을 함께 측정한 뒤 조정해야 합니다.

Data lifecycle

모델·차원·기존 데이터의 생명주기를 함께 설계한다

  • 임베딩을 켠 이후의 신규 문제는 저장 시 벡터가 함께 색인됩니다.
  • 비활성 기간에 저장된 기존 문제는 자동으로 백필되지 않습니다.
  • 512차원을 바꾸면 DB 컬럼 타입과 API 설정을 같은 마이그레이션에서 변경해야 합니다.
  • 임베딩 모델이 바뀌면 서로 다른 모델의 벡터를 같은 임계값으로 비교할지 정책이 필요합니다.
  • 백필은 API rate limit, 비용, 재시작, 진행률과 멱등성을 고려한 배치 작업이어야 합니다.
03
Verification

Testcontainers 실제 DB 통합 테스트

“도입했다”가 아니라 운영과 같은 DB 타입·마이그레이션·검색 SQL이 실제로 동작함을 자동 테스트로 증명합니다.

Learning goal

이번 회차가 끝나면 설명할 수 있어야 하는 것

  • H2의 PostgreSQL 호환 모드로 pgvector 전용 기능을 검증할 수 없는 이유
  • Testcontainers가 고정 로컬 DB보다 재현성과 격리를 높이는 방식
  • Flyway V1~V3와 실제 Repository SQL의 검증 경계
  • 임베딩 API 없이 결정적인 벡터 테스트를 만드는 이유
  • 단위 테스트와 인프라 통합 테스트를 분리하는 이유

Why not H2

SQL 문법 호환과 실제 DB 기능 호환은 다르다

검증 대상H2실제 pgvector 컨테이너
일반 테이블·FK·유니크 제약가능가능
CREATE EXTENSION vector불가가능
vector(512) 타입불가가능
<=> 코사인 거리불가가능
USING hnsw불가가능

H2는 빠른 도메인 테스트에 계속 사용합니다. PostgreSQL 전용 기능만 느리지만 실제와 동일한 통합 테스트로 분리하는 것이 목적입니다.

Container lifecycle

테스트가 직접 일회용 DB를 준비한다

pgvector 이미지 시작

Flyway V1~V3 적용

완전히 빈 DB에서 실제 운영과 같은 순서로 스키마를 생성합니다.

DB 카탈로그 검증

vector 확장, vector(512), HNSW와 vector_cosine_ops를 확인합니다.

Repository SQL 실행

실제 CAST(? AS vector), upsert, 코사인 검색과 0.90 임계값을 실행합니다.

컨테이너 제거

개발자의 5432/5433 포트와 기존 데이터에 영향을 주지 않고 종료합니다.

Deterministic fixture

실제 API 대신 결과를 예측할 수 있는 고정 벡터를 쓴다

기존 벡터: [1.00, 0.00, 0, 0, ...]
유사 벡터: [0.99, 0.10, 0, 0, ...]  // cosine ≈ 0.995 → 차단
다른 벡터: [0.00, 1.00, 0, 0, ...]  // cosine = 0     → 통과

이 테스트는 외부 모델의 응답 변화나 API 키, 네트워크, 요금에 영향을 받지 않습니다. 대신 DB 타입·연산자·SQL·임계값 로직을 동일한 입력으로 반복 검증합니다.

Honest boundary

이 테스트가 증명하는 것과 증명하지 않는 것

증명하는 것

  • Flyway V3가 실제 DB에서 적용됨
  • 512차원 벡터와 HNSW 생성
  • Repository 코사인 SQL의 실행 가능성
  • 0.90 임계값 분기
  • 임베딩 장애 시 SHA-256 폴백

아직 증명하지 않는 것

  • 한국어 임베딩의 실제 의미 품질
  • 0.90의 최적 정밀도·재현율
  • 대규모 HNSW p95 성능
  • 실제 API 네트워크·한도·과금
  • 모델 변경 시 벡터 호환성
Interview

면접에서 연결할 질문

기술 이름보다 문제·선택·trade-off·검증 순서로 답하는 것이 핵심입니다.

Q. 왜 Elasticsearch 대신 pgvector를 선택했나요?

문제 원본과 의미 벡터의 이중 쓰기 정합성을 줄이고, 현재 규모에서 별도 검색 클러스터의 운영 부담보다 PostgreSQL 통합의 이점이 크다고 판단했다고 답합니다.

Q. 정확 해시가 있는데 임베딩이 필요한가요?

해시는 동일 문자열 계열에 강하고 임베딩은 표현이 다른 의미 중복 후보를 보완하므로, 저비용 계층을 먼저 적용한 뒤 선택 기능을 추가했다고 설명합니다.

Q. HNSW가 항상 정확한 결과를 반환하나요?

근사 검색이라 완전 탐색과 같은 재현율을 보장하지 않으며, 후보 폭과 검색 지연을 교환합니다. 실제 데이터로 recall과 p95를 함께 측정해야 합니다.

Q. 왜 H2 테스트만으로 충분하지 않나요?

호환 모드는 PostgreSQL 확장 타입·연산자·HNSW를 구현하지 않으므로, 빠른 테스트는 유지하고 해당 경계만 Testcontainers의 실제 DB로 검증했다고 답합니다.

Q. 임베딩 서비스가 장애 나면 어떻게 되나요?

의미 중복 검사는 건너뛰되 SHA-256 정확 중복 제약과 퀴즈 생성은 계속 동작합니다. 품질 저하는 허용하지만 핵심 가용성은 유지하는 선택입니다.

Q. 0.90과 512는 어떤 근거인가요?

저장·검색 비용을 고려한 초기값이며 최종 근거가 아니라고 명확히 합니다. 라벨링한 문항 쌍으로 임계값과 차원을 비교 평가하는 것이 다음 단계입니다.

Glossary

핵심 용어

Embedding
텍스트·이미지 같은 대상을 의미 관계가 보존되도록 숫자 벡터로 표현한 것
Dimension
벡터를 구성하는 숫자 축의 개수. 이 프로젝트는 512개
Cosine distance
두 벡터 방향 차이를 거리로 표현한 값. pgvector 연산자는 <=>
ANN
Approximate Nearest Neighbor. 정확도를 일부 교환해 가까운 벡터를 빠르게 찾는 방식
HNSW
벡터를 다층 근접 그래프로 연결해 탐색하는 ANN 인덱스
pgvector
PostgreSQL에 벡터 타입·거리 연산·ANN 인덱스를 추가하는 확장
Testcontainers
테스트 중 실제 DB·브로커 같은 의존성을 일회용 컨테이너로 제공하는 라이브러리
Flyway
SQL 마이그레이션 파일을 버전 순서로 적용하고 이력을 관리하는 DB 변경 도구
Fallback
선택 기능이 실패했을 때 핵심 기능을 유지하기 위한 대체 처리 경로
