# Auknowlog 포트폴리오 완성도·부족한 부분 점검

> 점검 기준일: 2026-09-07
> 이 문서는 현재 상태의 진단 기록이다. 실제 작업 순서와 상태는 [개선 로드맵](IMPROVEMENT_ROADMAP.md)에서 관리한다.

## 1. 현재 평가

- 기술 포트폴리오 완성도: **약 68%**
- 실제 서비스 운영 완성도: **약 40%**
- 현재 단계: 핵심 백엔드 기술을 설명할 수 있는 데모는 가능하지만, 사용자가 반복해서 쓰는 제품 흐름과 재현 가능한 배포는 부족하다.

점수는 절대적인 품질 수치가 아니라, 면접관이 저장소를 내려받아 실행하고 기술 선택의 결과를 확인할 수 있는지를 기준으로 한 우선순위 지표다.

| 평가 영역 | 배점 | 현재 | 판단 근거 |
| --- | ---: | ---: | --- |

| 테스트·재현성 | 15 | 9 | 백엔드 14개 테스트 통과, 프론트엔드 테스트 0개와 빌드 환경 문제 |

| 합계 | 100 | **68** | 포트폴리오 데모 단계 |

## 2. 현재 강점

- OpenAI Responses API의 구조화 출력을 이용한 객관식 퀴즈 생성
- SHA-256 정확 중복과 pgvector 코사인 유사도를 결합한 중복 방지
- Flyway로 V1~V3 데이터베이스 변경 이력 관리
- 퀴즈, 문항, 풀이, 문항별 답안, 복습 일정을 관계형 도메인으로 분리
- AI 모델, 성공·실패, 토큰 수, 지연시간 원장 기록
- Testcontainers의 실제 PostgreSQL 16 + pgvector에서 마이그레이션과 HNSW 검색 검증
- GitHub Actions에서 백엔드 단위·통합 테스트 실행
- 외부 접속을 기본 비활성화하고 인증 프록시 뒤에 Quick Tunnel 배치
- 스택 변경 이유, 트레이드오프와 검증 방법을 문서로 기록

## 3. P0 — 포트폴리오 공개 전에 반드시 보완

### 3.1 실행 환경 재현성

**현재 문제**

- 프론트엔드는 Node `^20.19.0 || >=22.12.0`을 요구하지만, 로컬 기본 Node 21.6.2가 제거된 ICU 73 라이브러리를 참조해 `npm run build`가 실패한다.
- `npm`과 `pnpm` 흔적이 함께 있으며 실행 도구가 명확하지 않다.
- 네이티브 PostgreSQL은 `5432`, Docker pgvector는 `5433`을 사용하지만 애플리케이션 기본값은 `5432`다.
- Docker Compose는 DB만 실행하고 백엔드·프론트엔드는 호스트 환경에 의존한다.

**개선 방향**

1. Node 22 LTS를 `.nvmrc` 또는 `.tool-versions`로 고정한다.
2. 패키지 관리자를 `pnpm` 또는 `npm` 하나로 통일하고 하나의 lock 파일만 유지한다.
3. 이 개발 환경에서는 프로젝트 DB를 `5433`으로 명시하고 Compose·백엔드 기본값·문서를 일치시킨다.
4. 백엔드와 프론트엔드 Dockerfile을 추가하고 전체 Compose 실행 경로를 제공한다.
5. CI에 프론트엔드 의존성 설치와 프로덕션 빌드를 추가한다.

**완료 기준**

- 새 환경에서 문서에 적힌 한 가지 명령으로 전체 서비스를 실행할 수 있다.
- 로컬 도구 설치 상태와 관계없이 프론트엔드·백엔드 빌드가 성공한다.
- 애플리케이션이 어느 PostgreSQL에 연결되는지 한 곳에서 확인할 수 있다.

### 3.2 핵심 학습 흐름 완성

**현재 문제**

- 풀이와 복습 일정은 DB에 저장되지만 사용자가 다시 조회할 API와 화면이 없다.
- `review_schedule`은 오답마다 생성되지만 복습 완료와 다음 일정 계산이 없다.
- 학습 기록을 저장해도 사용자 입장에서는 다음 행동으로 이어지지 않는다.

**개선 방향**

```text
퀴즈 생성 → 풀이 제출 → 학습 이력 조회
          → 오늘의 복습 조회 → 재풀이 → 다음 복습일 계산
```

**완료 기준**

- 학습 이력 목록과 상세 결과를 조회할 수 있다.
- 오늘 복습할 문제를 조회하고 답안을 제출할 수 있다.
- 복습 결과에 따라 일정이 갱신되며 중복 PENDING 일정이 생성되지 않는다.
- 이 전체 흐름을 브라우저 E2E 테스트로 검증한다.

### 3.3 프론트엔드 품질 기반

**현재 문제**

- `QuizGenerator.vue` 하나가 자료 저장, 생성, 제출, 채점, Markdown·Notion·Git 저장을 모두 담당한다.
- 프론트엔드 자동 테스트가 없다.
- Vue 초기 템플릿 파일이 남아 있어 저장소의 완성도를 낮춘다.

**개선 방향**

- `QuizCreateForm`, `QuizQuestionList`, `QuizResult`, `LearningHistory`, `ReviewQueue`, `SourceLibrary`로 화면 책임을 분리한다.
- HTTP 호출과 상태 전이를 composable로 분리한다.
- Vitest와 Vue Test Utils로 제출 전 정답 비노출, 전체 답안 검증, 오류 상태를 테스트한다.
- Playwright로 생성 → 제출 → 저장 → 복습 핵심 흐름을 검증한다.

**완료 기준**

- 프론트엔드 프로덕션 빌드와 테스트가 CI에서 통과한다.
- 단일 컴포넌트가 외부 저장과 학습 상태를 동시에 관리하지 않는다.
- 로딩, 빈 결과, 오류, 재시도 상태가 화면에 일관되게 표시된다.

### 3.4 전체 기능 기준 프론트엔드 상세 점검

현재 프론트엔드는 퀴즈를 생성하고 푸는 데모 화면으로는 동작한다. 그러나 백엔드에 저장되는 학습 자료, 풀이 이력, 오답 복습을 사용자가 다시 활용할 화면이 없어 제품의 핵심 가치인 **반복 학습**이 UI에서 끊긴다.

| 제품 기능 | 현재 화면에서 가능한 것 | 부족한 부분 | 목표 화면·흐름 |
| --- | --- | --- | --- |
| 퀴즈 생성 | 주제, 문항 수, 데모/AI 모드 선택 | 난이도·문항 유형 설정이 없고 유료 API 모드의 비용·실패 가능성이 충분히 드러나지 않음 | 생성 조건 요약, AI 비용 경고, 생성 취소·재시도 |
| 학습 자료 | 제목과 본문을 입력해 생성 직전에 저장 | 목록·상세·재사용·삭제가 없으며 퀴즈 생성 실패 시 이미 저장된 자료가 남을 수 있음 | `SourceLibrary`에서 자료를 관리하고 기존 자료를 선택해 퀴즈 생성 |

| 학습 이력 | 없음 | DB의 `learning_attempt`와 문항별 답안을 조회할 수 없음 | 날짜·주제별 이력, 상세 답안, 정답률 추세 |

| 장애 처리 | 문자열 오류 메시지 표시 | API별 오류 형식이 다르고 일부 객체 응답은 `[object Object]`로 보일 수 있으며 재시도·복구 동작이 없음 | 공통 API 오류 모델, 상태 코드별 안내, 안전한 재시도 |

#### P0 — 가장 먼저 고칠 프론트엔드 문제

1. **모바일 레이아웃 정상화**

   - `QuizGenerator.vue`의 `.quiz-container`에 `min-width: 800px`가 있어 작은 화면에서 가로 스크롤이 발생한다.
   - 모바일 외부 접속을 프로젝트 기능으로 제공하므로 반응형 지원은 선택적인 디자인 개선이 아니라 기능의 완료 조건이다.
   - 최소 폭을 제거하고 360px, 768px, 1280px 뷰포트에서 입력 폼, 선택지, 하단 작업 버튼을 검증한다.

2. **제출과 학습 기록 저장 통합**

   - 현재 `submitQuiz()`는 클라이언트 채점만 하고 `saveLearningAttempt()`를 따로 눌러야 DB 저장과 오답 예약이 실행된다.
   - 사용자가 첫 버튼만 누르면 화면에는 “채점 완료”가 보이지만 학습 기록은 남지 않는 조용한 실패가 된다.
   - 서버 제출 API가 채점·풀이 저장·복습 예약 결과를 한 번에 반환하고, 프론트엔드는 그 응답을 기준으로 결과를 그리도록 변경한다.

3. **정답 비공개 API 계약**

   - CSS나 `v-if`로 숨기는 것은 화면 표시만 막을 뿐이다. 현재 `QuizResponse`에는 `correctAnswer`와 `explanation`이 포함돼 네트워크 응답에서 확인할 수 있다.
   - 생성 DTO는 문항 ID·본문·선택지만 반환하고, 제출 뒤 결과 DTO에서 정답·해설·정오 여부를 반환하도록 분리한다.
   - 이 변경은 “시험 보안”뿐 아니라 채점 책임을 서버 한 곳에 두어 데이터 정합성을 높인다.

4. **작업별 비동기 상태 분리**

   - 하나의 `loading` 값이 생성, 풀이 저장, Git 저장을 모두 제어해 어떤 작업이 진행 중인지 정확히 표현하지 못한다.
   - `generating`, `submitting`, `exporting` 상태를 분리하고 요청 중복 방지, 버튼별 진행 문구, 재시도 가능 여부를 각각 관리한다.
   - AI 생성 요청에는 취소 또는 타임아웃 안내를 제공하고, 화면 이동 전 저장되지 않은 풀이가 있으면 확인한다.

5. **프론트엔드 실행 환경 복구와 자동 검증**

   - 2026-09-08 재검증에서도 로컬 Node 21.6.2가 제거된 ICU 73 라이브러리를 참조해 `node -v`와 `npm run build`가 실행 전에 실패했다.
   - Node 22 LTS와 패키지 관리자를 고정한 뒤 CI에서 `build`, 단위 테스트, 모바일·데스크톱 E2E 테스트를 실행한다.

#### P1 — 화면 구조와 유지보수성 개선

- 889줄인 `QuizGenerator.vue`를 생성 폼, 문제 풀이, 결과, 내보내기 책임으로 분리한다.
- 세 저장 함수에서 반복되는 답안·통계 payload 조립을 하나의 함수나 composable로 합친다.
- 연결되지 않은 `saveQuizAsMarkdown`, `saveQuizToNotion`은 실제 내보내기 UI에 연결하거나 제거한다.
- Vue 초기 템플릿의 `base.css`, `main.css`, 사용하지 않는 Welcome·아이콘 컴포넌트를 정리한다. 특히 데스크톱에서 `#app`을 2열 Grid로 만드는 초기 템플릿 규칙과 현재 App 스타일의 충돌을 제거한다.
- 인라인 Git 버튼 색상처럼 컴포넌트 안에 흩어진 표현을 디자인 토큰과 공통 버튼 variant로 통합한다.
- 오류 성공 여부를 문자열에 `실패`가 포함됐는지로 판단하지 않고 `{ type, code, message }` 상태로 관리한다.
- 입력 주제는 `trim()` 기준으로 검증하고, 자료 길이 제한과 서버 제약을 폼에서 안내한다.

#### P1 — 접근성·사용성 개선

- 오류·저장·채점 결과 영역에 `role="alert"` 또는 `aria-live`를 적용해 화면 낭독기가 상태 변화를 알 수 있게 한다.
- API 오류 발생 시 오류 영역으로, 미응답 제출 시 첫 미응답 문항으로 포커스를 이동한다.
- 입력 포커스에서 `outline: none`만 적용하지 말고 명확한 `:focus-visible` 표시를 제공한다.
- 객관식 문항을 `fieldset`·`legend`와 라디오 그룹 의미로 표현하거나 현재 버튼 그룹에 문항별 접근성 이름을 제공한다.
- 정답·오답을 색상만으로 구분하지 않고 텍스트와 아이콘을 계속 함께 사용하며 대비를 자동 검사한다.
- 생성 중 스켈레톤 또는 진행 안내, 빈 이력·빈 복습 목록의 다음 행동, 모바일 하단 제출 영역을 제공한다.

#### P2 — 실제 데이터가 쌓인 뒤 추가할 기능

- 대시보드: 오늘의 복습 수, 최근 정답률, 주제별 약점, 반복 오답을 표시한다.
- 출처 탐색: `sourceReferences`를 단순 문자열로 나열하지 않고 원문 청크를 열어 근거를 확인하게 한다.
- 검색·필터: 학습 이력과 자료가 충분히 쌓였을 때 서버 페이지네이션, 주제·기간·정답률 필터를 추가한다.
- 사용자 설정: 기본 문항 수, 기본 생성 모드, 접근성 선호를 저장한다.
- 운영 진단: 관리자 화면 대신 개발 모드 진단 패널에서 모델, 생성 지연, 중복 제거 수, 토큰 사용량을 확인한다.

#### 스택 도입 기준

| 후보 | 도입 시점 | 이 프로젝트에서의 타당한 이유 |
| --- | --- | --- |
| TypeScript | 컴포넌트 분리와 DTO 재설계 시 | nullable 퀴즈, 문항 ID, 제출 전·후 응답 타입 차이를 컴파일 단계에서 검증할 수 있음 |
| Vue Router | 이력·복습·자료 관리가 독립 화면이 될 때 | 단일 컴포넌트 조건부 렌더링보다 URL로 화면 상태를 재현하고 새로고침·뒤로가기를 지원하기 적합 |
| TanStack Query for Vue | 조회 API와 서버 상태가 3개 이상 생길 때 | 이력·복습·자료의 로딩, 오류, 캐시 무효화, 재조회 로직을 중복 구현하지 않게 함 |
| Pinia | 로그인 사용자, 전역 설정처럼 여러 화면이 함께 수정하는 클라이언트 상태가 생길 때 | 현재 단일 화면에는 과하지만 화면 간 공유 상태가 생기면 책임이 명확해짐 |
| Vitest + Vue Test Utils | 프론트 리팩터링 시작과 동시에 | 제출 상태, 오류 분기, 컴포넌트 계약을 빠르게 회귀 검증 |
| Playwright | 생성→제출→복습 흐름이 연결될 때 | 실제 브라우저와 모바일 뷰포트에서 API·라우팅·접근성 흐름까지 검증 |

유행만을 이유로 상태 관리 라이브러리나 UI 프레임워크를 먼저 추가하지 않는다. 현재는 반응형 CSS 수정, 서버 중심 제출 흐름, 컴포넌트 분리와 테스트가 더 직접적인 효과를 낸다.

#### 권장 적용 순서

```text
1단계: Node·CSS 충돌 정리 → 모바일 반응형 → Vitest 기반 추가
2단계: 제출 API 재설계 → 서버 채점·자동 저장 → 정답 비공개
3단계: Router 도입 → 학습 이력 → 오늘의 복습 → 자료 보관함
4단계: Git 내보내기 확인 화면 → 오류·접근성 정리 → Playwright E2E
5단계: 실제 사용 데이터 기반 대시보드와 성능 최적화
```

**프론트엔드 완료 기준**

- 360px 모바일부터 데스크톱까지 가로 스크롤 없이 핵심 기능을 사용할 수 있다.
- 답안 제출 한 번으로 서버 채점, 풀이 저장, 오답 예약이 완료된다.
- 정답과 해설은 제출 전 API 응답에 포함되지 않는다.
- 생성, 제출, 내보내기의 로딩·오류·재시도 상태가 서로 독립적이다.
- 퀴즈 생성 → 제출 → 이력 확인 → 복습 완료 흐름을 Playwright로 검증한다.
- 프론트엔드 build, unit test, E2E가 CI에서 재현 가능하게 통과한다.

## 4. P1 — 기술적 차별화를 위해 보완

### 4.1 학습 자료 기능을 완성하거나 제거

**현재 문제**

- 자료 생성 API만 있고 목록·상세·수정·삭제·재사용 기능이 없다.
- 같은 자료로 다시 생성하면 `source_document`가 중복될 수 있다.
- 자료가 길어도 앞의 청크 최대 4개만 사용하므로 질문과 관련 없는 내용이 전달될 수 있다.
- 실제 DB의 `source_document`, `source_chunk` 데이터는 현재 0건이다.

**선택지 A — 기능 완성**

- 자료 목록과 재사용 UI
- 콘텐츠 해시 기반 중복 자료 방지
- 질문·주제와 관련 있는 Top-K 청크 검색
- 생성 문항의 출처 청크 표시
- 자료 삭제 시 연관 데이터 정책 검증

**선택지 B — 범위 축소**

- 자료 기반 생성 기능과 관련 테이블을 제거하고 주제 기반 퀴즈·복습 품질에 집중한다.

포트폴리오에서는 절반만 연결된 기능보다, 선택 이유와 검증 결과가 분명한 작은 범위가 낫다.

### 4.2 AI 비용과 품질 제어

**현재 문제**

- 토큰 사용량은 기록하지만 요청을 차단하는 예산 정책은 없다.
- 터널 인증 사용자는 제한할 수 있어도 인증 후 AI API 반복 호출은 별도로 제한되지 않는다.
- 라이브 OpenAI 호출을 CI에서 실행하지 않는 것은 타당하지만, 대표 입력에 대한 오프라인 품질 평가가 없다.

**개선 방향**

- 요청당 최대 문제 수·출력 토큰·입력 컨텍스트 예산을 서버에서 강제한다.
- 일별 생성 횟수 또는 비용 상한과 `429` 응답을 적용한다.
- 대표 주제 평가셋으로 JSON 스키마 준수율, 중복 차단율, 근거 일치율을 측정한다.
- AI 장애, 임베딩 장애, DB 장애를 분리해 사용자 메시지와 지표에 기록한다.

### 4.3 제품 인증과 데이터 소유권

**현재 문제**

- Quick Tunnel 세션은 개발 화면을 보호하는 공용 출입증이며 Auknowlog 사용자 계정이 아니다.
- 퀴즈·풀이·복습 테이블에 사용자 식별자가 없어 다중 사용자 데이터를 분리할 수 없다.
- 로컬 Git 명령을 이용한 저장은 개인 개발 환경에서는 동작하지만 공개 서비스 권한 모델로는 부적합하다.

**개선 방향**

- 공개 포트폴리오를 단일 사용자 데모로 둘지, 사용자 로그인 서비스로 만들지 먼저 결정한다.
- 다중 사용자라면 Spring Security/OIDC와 `user_id` 기반 소유권 검증을 적용한다.
- Git 내보내기는 대상 저장소와 커밋 내용을 확인하는 명시적 작업으로 분리한다.

## 5. P2 — 운영 설득력과 유지보수성 보완

### 5.1 데이터 모델 정리

- `question_history`와 `learning_question`에 중복 저장되는 문제 원문의 소유권을 결정한다.
- 선택지와 출처의 JSON 문자열을 그대로 검색할 필요가 있다면 PostgreSQL `JSONB` 전환을 검토한다.
- 복습 일정의 중복 PENDING 방지 제약과 상태 전이 규칙을 추가한다.
- Flyway로 데이터 마이그레이션과 롤백 전략을 문서화한다.

### 5.2 관측과 장애 대응

- Actuator 메트릭을 실제 대시보드 또는 운영 리포트로 연결한다.
- AI 성공률, p95 지연, 토큰 비용, 중복 차단률에 임계값을 둔다.
- 구조화 로그와 요청 상관관계 ID를 적용한다.
- 포트폴리오 문서에 실제 장애 사례, 원인, 수정, 재발 방지 테스트를 남긴다.

### 5.3 문서 정합성

- `PROJECT_OVERVIEW.md`의 Elasticsearch 설명을 현재 pgvector 구조로 수정한다.
- `IMPROVEMENT_ROADMAP.md`의 pgvector 통합 테스트 상태를 실제 완료 결과와 일치시킨다.
- README의 실행 명령과 실제 Node·DB 포트를 자동 검증한다.

## 6. 지금 추가하지 않을 기술

다음 기술은 문제와 측정 근거가 생기기 전에는 포트폴리오 장식 목적으로 추가하지 않는다.

- Kubernetes: 단일 인스턴스 개발·데모의 배포 복잡도만 증가
- Elasticsearch·Kibana: 현재 의미 중복 검색은 pgvector 하나로 충족
- Redis: 캐시 적중률, 분산 락, 큐 같은 구체적 요구가 아직 없음
- 마이크로서비스: 현재 도메인 규모에서는 트랜잭션과 운영 복잡도가 더 커짐

필요성이 생기면 먼저 해결할 문제, 예상 효과, 대안, 측정 지표를 기록한 뒤 도입한다.

- 공개 환경의 인증, AI 호출 제한, 비밀정보 관리 적용
