01 · Why

문제와 해결 방향

공유기 포트 포워딩이나 서버 전체 공개 없이, 짧은 확인 시간 동안만 외부에서 접속하는 것이 목표다.

BEFORE

로컬 네트워크에 묶인 화면

  • 127.0.0.1:5173은 맥북에서만 접근 가능
  • 다른 Wi-Fi나 모바일 데이터에서는 확인 불가
  • Vite 포트를 그대로 공개하면 개발 서버가 인터넷에 노출됨
AFTER

선택형 인증 Quick Tunnel

  • 기본 모드는 여전히 로컬 전용
  • 필요할 때 임시 HTTPS URL만 생성
  • 모든 요청이 로그인·세션 검증을 통과해야 앱에 도달

02 · Architecture

전체 요청 경로

인터넷에 보이는 것은 Cloudflare가 발급한 임시 HTTPS 주소뿐이다. 로컬 서비스는 모두 루프백 주소에 남는다.

핵심

공유기에서 인바운드 포트를 열지 않는다. PostgreSQL과 OpenAI API 키도 외부로 전달되지 않으며, 백엔드가 필요한 요청만 내부에서 처리한다.

통신 구간연결 방식보호·신뢰 경계
브라우저 → Cloudflare공개 인터넷의 HTTPSTLS로 암호화되며 Cloudflare Edge가 HTTPS 요청을 받는다.
Cloudflare → cloudflared맥북이 먼저 만든 아웃바운드 터널보통 7844 포트의 QUIC 또는 HTTP/2 연결을 사용한다. 공유기 인바운드 포트는 열지 않는다.
cloudflared → 인증 프록시127.0.0.1:4180맥북 내부 루프백 통신이다. Cloudflare는 외부 HTTPS 종단이므로 신뢰하는 중계자에 포함된다.
인증 프록시 → Vite → Spring Boot로컬 HTTP 프록시세션 검증을 통과한 요청만 화면과 API까지 전달한다.

03 · Runtime Flow

시작부터 종료까지

아래 탭을 선택하면 시작, 사용자 로그인, 인증 후 전달, 종료 흐름을 단계별로 확인할 수 있다.

  1. 1

    모드 선택

    quick-tunnel 명령을 명시적으로 실행한다. 기본값은 외부 공개가 없는 local이다.

  2. 2

    사전 확인

    Node.js, cloudflared, curl, OpenSSL과 프론트엔드·백엔드 Health 응답을 확인한다.

  3. 3

    자체 테스트

    인증 우회 차단, 보안 쿠키, 헤더 제거, 로그인 실패 제한 테스트를 먼저 실행한다.

  4. 4

    비밀정보 생성

    임시 비밀번호 128비트와 세션 토큰 256비트를 OpenSSL의 안전한 난수로 생성한다.

  5. 5

    인증 프록시 시작

    127.0.0.1:4180에만 바인딩하고, 실제 시작한 프로세스가 살아 있는지 검증한다.

  6. 6

    로컬 검증

    미인증 요청은 302, 유효 세션 요청은 200인지 확인한다.

  7. 7

    Quick Tunnel 시작

    cloudflared가 인증 프록시로 향하는 아웃바운드 터널과 임시 HTTPS URL을 만든다.

  8. 8

    외부 검증

    공개 URL에서도 미인증 302와 인증 성공 200을 확인한 뒤 URL과 인증 정보를 표시한다.

No · 로그인 필요

302로 로그인 화면에 보낸다. 제출 횟수가 제한을 넘으면 429, 인증 정보가 다르면 403을 반환한다. 어느 경우에도 앱은 요청을 받지 않는다.

성공 · 세션 발급

사용자명과 비밀번호가 모두 맞으면 Secure·HttpOnly·SameSite=Strict 쿠키를 발급하고 원래 요청 경로로 303 이동한다.

  1. 1

    세션 재검증

    화면·API·WebSocket 요청마다 세션 토큰을 다시 확인한다.

  2. 2

    인증정보 제거

    터널 세션 쿠키와 외부 Authorization 헤더를 업스트림 요청에서 제거한다.

  3. 3

    Vite 전달

    인증된 요청만 127.0.0.1:5173으로 프록시한다. 화면 자원과 HMR WebSocket도 같은 규칙을 따른다.

  4. 4

    백엔드 처리

    /api 요청은 기존 Vite 설정을 통해 Spring Boot로 전달되고, 결과가 같은 경로를 거쳐 사용자에게 돌아간다.

  1. 1

    종료 조건

    stop, local, Ctrl+C, 프로세스 오류 또는 기본 8시간 만료가 종료를 시작한다.

  2. 2

    프로세스 식별

    PID뿐 아니라 예상 명령행도 확인해 관계없는 프로세스를 종료하지 않는다.

  3. 3

    연결 종료

    cloudflared와 인증 프록시를 순서대로 종료해 외부 요청 경로를 닫는다.

  4. 4

    정보 폐기

    공개 URL과 인증 정보 파일을 삭제한다. 프로세스가 사라져 기존 세션 토큰도 즉시 무효가 된다.

04 · Authentication

비밀번호, 세션 토큰, 쿠키의 역할

현재 구현은 API의 Authorization 헤더가 아니라 브라우저가 자동 관리하는 세션 쿠키를 사용한다. 단, 쿠키도 실제 HTTP 요청에서는 Cookie 헤더로 전달된다.

AUTHORIZATION HEADER

클라이언트 코드가 토큰을 직접 붙임

Authorization: Bearer <access-token>
  • 프론트엔드 코드나 모바일 앱이 저장·첨부를 관리한다.
  • REST API, 모바일 앱, 서버 간 통신에 잘 맞는다.
  • 브라우저가 자동 전송하지 않아 일반적인 CSRF 노출은 낮지만, JavaScript 저장소에 둔 토큰은 XSS 탈취에 주의해야 한다.
  • 이 터널 인증에는 사용하지 않는다. 외부에서 들어온 헤더는 업스트림 전달 전에 제거한다.
SESSION COOKIE · CURRENT

브라우저가 세션 증명을 자동 전송

Set-Cookie: auknowlog_tunnel_session=<token>;
  HttpOnly; Secure; SameSite=Strict

Cookie: auknowlog_tunnel_session=<token>
  • 로그인 성공 응답을 받은 브라우저가 쿠키를 저장한다.
  • 같은 사이트의 이후 화면·API·WebSocket 요청에 자동으로 포함한다.
  • HttpOnly로 JavaScript 접근을 막고, Secure로 HTTPS에서만 전송하며, SameSite=Strict로 교차 사이트 전송을 제한한다.
  • 현재 임시 브라우저 로그인 흐름에 사용한다.

프록시가 “토큰을 만든다”는 뜻

토큰은 사용자 정보가 들어 있는 JWT가 아니다. 터널 시작 스크립트가 OpenSSL의 암호학적으로 안전한 난수로 만든, 의미 없는 일회성 비밀 문자열이다. 프록시는 이 값을 기억하고 쿠키 값과 일치하는지만 확인한다.

  1. 1

    실행마다 생성

    임시 비밀번호는 16바이트(128비트), 세션 토큰은 32바이트(256비트) 난수로 생성한다.

  2. 2

    프록시에 전달

    세션 토큰은 환경 변수로 인증 프록시 프로세스에 전달되고 실행 중 메모리에서 비교 기준으로 사용된다.

  3. 3

    로그인 제출

    사용자는 임시 사용자명·비밀번호를 한 번 입력한다. 실패는 식별자별 횟수를 제한한다.

  4. 4

    쿠키 발급

    인증 정보가 맞으면 프록시가 같은 세션 토큰을 보안 쿠키로 브라우저에 전달한다.

  5. 5

    자동 첨부

    이후 브라우저가 요청의 Cookie 헤더에 토큰을 자동으로 넣는다. 비밀번호를 매번 보내지 않는다.

  6. 6

    매 요청 검증

    프록시는 HTTP와 WebSocket 요청마다 쿠키를 꺼내 보관 중인 토큰과 고정 시간으로 비교한다.

  7. 7

    분리 후 전달

    검증에 성공하면 터널 쿠키와 외부 인증 헤더를 제거한 뒤 Vite로 전달한다. 앱의 다른 쿠키는 유지한다.

  8. 8

    종료 시 무효화

    터널·프록시 종료 또는 기본 8시간 만료 후 비교 대상이 사라진다. 다음 실행은 새 토큰을 만들므로 기존 쿠키는 통하지 않는다.

이름용도저장·수명서로 다른 점
임시 비밀번호최초 로그인에서 사용자 확인실행마다 생성, 로컬 런타임 파일과 프록시 메모리사용자가 입력하며 매 요청에는 보내지 않는다.
터널 세션 토큰로그인 완료 사실을 증명프록시 메모리와 브라우저 쿠키, 최대 8시간현재 구현은 로그인마다 별도 발급하지 않고 터널 하나가 하나의 토큰을 공유한다.
OpenAI API 키백엔드가 OpenAI API 비용·권한 계정을 증명백엔드 환경 변수외부 접속 인증과 무관하며 브라우저나 터널로 보내지 않는다.
Cloudflare 터널 자격정보정식 Named Tunnel에서 계정·터널 식별해당 구성을 사용할 때 cloudflared가 관리현재 Quick Tunnel은 임시 URL 방식이라 애플리케이션 로그인 토큰과 별개다.

05 · Security

보안 경계와 방어 수단

임시 URL 자체는 비밀정보로 취급하지 않는다. URL을 알아도 인증을 통과하지 못하면 애플리케이션에 접근할 수 없도록 설계했다.

강한 임시 비밀정보

실행마다 32자리 16진수 비밀번호와 64자리 세션 토큰을 새로 생성한다.

고정 시간 비교

crypto.timingSafeEqual로 사용자 입력을 비교해 시간 차이를 통한 추측 가능성을 줄인다.

로그인 횟수 제한

식별자별 5분 동안 5회 실패하면 429 Too Many Requests로 차단한다.

보안 세션 쿠키

JavaScript 접근 차단, HTTPS 전용, 교차 사이트 전송 제한 속성을 함께 설정한다.

응답 보안 헤더

no-store, CSP, 프레임 차단, MIME 추측 방지, referrer 차단을 적용한다.

최소 로그

인증 실패 사실만 남기며 입력값, IP, 어느 필드가 맞았는지는 기록하지 않는다.

로컬 전용 바인딩

인증 프록시와 기존 서버는 127.0.0.1에서만 대기한다.

런타임 정보 격리

.runtime/은 Git에서 제외하고 디렉터리 700, 파일 600 권한을 사용한다.

실패 시 닫힘

사전 검사나 공개 검증 하나라도 실패하면 시작한 프로세스와 인증 정보를 정리한다.

대상인터넷 직접 노출접근 조건설명
임시 Cloudflare URL공개HTTPS외부에 보이는 유일한 진입점
인증 프록시비공개cloudflared 또는 로컬모든 HTTP·WebSocket 요청의 인증 게이트
Vite 프론트엔드비공개유효한 터널 세션인증 프록시 뒤에서만 접근
Spring Boot API비공개Vite의 /api 경로별도 외부 포트를 열지 않음
PostgreSQL·pgvector비공개백엔드 내부 연결터널 경로에 포함되지 않음

06 · Changed Files

수정 내용과 책임

터널 수명주기, 인증, 테스트, 운영 문서를 분리해 각 파일의 역할이 섞이지 않게 했다.

scripts/tunnel-auth-proxy.mjs

07 · Runbook

실행과 확인 방법

프론트엔드와 백엔드가 먼저 실행 중이어야 한다. 터널은 애플리케이션 서버를 대신 실행하지 않는다.

# 대화형 모드 선택
./scripts/remote-access.sh

# 외부 접속 시작
./scripts/remote-access.sh quick-tunnel

# 실행 상태와 URL 확인
./scripts/remote-access.sh status

# 임시 인증 정보 확인
./scripts/remote-access.sh credentials

# 터널 종료 / 로컬 전용 전환
./scripts/remote-access.sh stop
./scripts/remote-access.sh local
OUTPUT

시작 성공 시 제공되는 정보

  • 매번 바뀌는 임시 HTTPS URL
  • 기본 사용자명 eunjuny
  • 매번 새로 생성되는 임시 비밀번호
  • 자동 종료 예정 시간
주의: 인증 정보는 터미널 출력과 로컬 런타임 파일에만 존재한다. 저장소, 문서, 메신저 공개 채널에 복사하지 않고 사용이 끝나면 즉시 stop한다.

08 · Trade-offs

어디까지 적합한가

이 구조는 혼자 쓰는 개발 화면의 임시 확인을 위한 선택이다. 정식 서비스 인증이나 배포를 대체하지 않는다.

상황권장 방식이유
몇 시간 동안 모바일에서 개발 화면 확인현재 Quick Tunnel설정이 빠르고 종료 시 공개 경로가 사라짐
내 기기들에서 반복적으로 비공개 접속Tailscale임시 공용 URL 없이 기기 단위 사설 네트워크 구성
포트폴리오를 상시 공개정식 배포 + 앱 인증고정 주소, 사용자 계정, 모니터링, 장애 대응과 접근 제어 필요
  • Quick Tunnel 주소는 실행할 때마다 바뀌며 가용성 보장이 없다.
  • 맥북, Docker, 프론트엔드와 백엔드가 실행 중이어야 한다.
  • 공유 인증 한 쌍만 제공하므로 사용자별 권한·로그아웃·계정 복구가 필요한 서비스에는 부족하다.
  • 인증 후에는 실제 OpenAI API 요청도 실행할 수 있으므로 API 예산 한도와 애플리케이션 요청 제한은 별도로 유지해야 한다.
